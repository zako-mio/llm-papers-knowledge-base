WebExplorer: Explore and Evolve for Training Long-Horizon Web Agents

标题（数据依据）：首页标题《WebExplorer: Explore and Evolve for Training Long-Horizon Web Agents》；arXiv: 2509.06501v3 [cs.CL]，2025-09-26。

作者与团队（数据依据）：Junteng Liu、Junxian He（HKUST）等，MiniMax 团队协作，Wenhu Chen（Waterloo）参与。

核心产出（数据依据）：数据合成方法 WebExplorer + 数据集 WebExplorer-QA（约 40K）+ 模型 WebExplorer-8B（基于 Qwen3-8B）。

本文定位：一份聚焦"如何用低成本方法造出难样例、再训练出长程连网 agent"的方法论文。全文 23 页，无独立 Limitations 章节。

说明：以下各处引用均以同目录《00-源数据提取.md》为唯一数字依据；凡属推理性质、数据表中未直接给出的解读性内容，均标注「（推断）」。

摘要

长程 web agent 的研究长期受制于一个现实矛盾：像 BrowseComp 这样能真实反映"跨多网站、多跳推理"难度的基准，靠人工整理，成本高、规模小，根本不足以支撑模型训练。开源训练数据要么规模不足，要么问题过简，训练出的模型一旦面对真实长程检索便迅速退化。本文作者提出一条数据合成新路线 WebExplorer：不做显式的图构建，而是用强 LLM 以 ReAct 范式从种子实体（取自 Wikipedia）出发，自主迭代地进行 search+browse，由模型自行决定何时停止并合成需跨多网站串联的初始 QA；随后用一套反向的"长到短"进化（Iterative Query Evolution）不断删减显式线索、模糊化关键信息，在答案不变的前提下把问题逼得更难。作者据此产出约 40K 的 WebExplorer-QA 数据集，先用约 13K 样本做 SFT 冷启动，再用 GRPO 强化学习（约 12K 样本、DeepSeek-V3 做判分 judge）微调出 WebExplorer-8B。结果在 8B 规模取得全面 SOTA：BrowseComp-en 15.7、BrowseComp-zh 32.0，超越 72B 的 WebSailor 乃至更大体量的 Kimi-K2；GAIA 50.0、WebWalkerQA 62.7、FRAMES 75.7（<100B 开源最佳），并意外地在 STEM 为主的 HLE 上获 17.3%，验证难查询训练的迁移价值。（300 字）

一、问题定位（Why / 为什么做这件事）

1.1 长程 web agent 评测与训练之间的"断层"

web agent 的目标是让模型在长连网状态下完成复杂的信息获取任务。要评测这种能力，业界需要类似 BrowseComp 这样的基准。但作者在 §2 中点出了一个尖锐的现实：BrowseComp 类基准的问题是"靠人工整理、成本高、规模小"，其中 BrowseComp-en 过半的 query 连人工标注者都需要投入 2 小时才能解决，「（推断）」这意味着这类基准天生就难以扩充规模，更不可能直接用作训练语料。评测基准与训练数据之间由此出现一道明显的断层：有了能衡量难度的标尺，却缺少能支撑训练的同难度数据。

1.2 既有开源训练数据的两个短板

作者把现有开源训练数据归纳为两个通病（§2）：一是规模不足，数据量撑不起一次像样的训练；二是难度过简，问题太接近单跳、单站检索，训练出来的模型无法适应需要跨多网站、多跳推理的真实场景。这两点彼此相关——正是因为人工造难样例成本太高，大家才只能退而求其次用简单数据，而简单数据又进一步限制了模型能触及的能力上限。

1.3 既有两条合成路线的局限

在数据合成上，已有工作主要分两条路线（§4），作者对它们的批评值得注意：

  • graph-based（WebSailor、WebShaper）：显式构建信息图（图节点+边），再在图上选子图、围绕子图出 QA。问题是节点扩展与选择启发式非常复杂，「（推断）」既要设计图结构，又要设计节点选择策略，还要处理图与问答的映射关系，工程与调参成本都很高。
  • evolution-based（迭代进化）：在已有 query 基础上不断注入新信息、把 query 越写越长。这条路线的问题是容易产生不自然的表述——为了变长而生硬堆砌，拼凑感强。

作者这两条路线的批评构成了全文动机的基石：graph-based 太复杂，short-to-long evolution 太生硬。作者想要的是一种既简单又不失自然、且能真正产出长程难样例的方法。

1.4 研究问题的清晰化

综合起来，作者要回答的核心问题是：如何在不依赖大量人工、也不依赖复杂图构建的前提下，规模化地合成"接近 BrowseComp 难度"的跨网站、多跳、信息自然编排的问答对，并由此训练出一个低成本的长程 web agent？

这是一个高度聚焦的工程+方法问题，其边界被作者明确限定：只做知识型 QA（Wikipedia 种子），不覆盖 STEM/多模态；只统一用 search/browse 两工具；只考察 8B 规模的模型能否拿 SOTA。

二、概念内核（What / 这篇论文在讲什么）

2.1 一句话归纳

WebExplorer 本质上是一套"先由强模型自主探索造出难问题、再把难问题反着越改越难"的数据合成管线，配合一套SFT+RL 的训练配方，最终得到一个 8B 规模但在多基准上超越 72B 乃至更大闭源模型的长程 web agent。

2.2 ReAct 范式（§2.1 Preliminaries）

作者先把任务形式化在 ReAct 框架下。轨迹表示为：

`

H_T = (τ0, α0, o0, τ1, α1, o1, ..., τT)

`

其中 τ 是推理文本（thought），α 是动作，o 是观测（工具返回）。动作 α_t ∈ {search, browse}，每个动作由"类型+参数"构成——search 的参数是 query 列表，browse 的参数是 URL 加抽取目标。

这套 scaffold 有两个工具（Appendix C）：

  • search：调用搜索引擎（Google），返回 top-10 结果（标题/URL/snippet）。
  • browse：用 Jina 抽取网页全文，再交给 Gemini 2.5 Flash 按给定的 browse query 作答（相当于让一个轻量模型在抽取文本里做定向阅读理解）。

「（推断）」这套 scaffold 的设计意图是把"找到哪个网页"（依赖强模型路径规划）和"读懂网页内容"（依赖抽取+轻量作答）分离，从而把 agent 的负担集中在"往哪走"这一长程规划环节。

2.3 Model-Based Exploration（§2.2，核心创新点一）

这一节是全文方法重点。作者的思路是：不做显式图构建，只用一个 prompt 让强 LLM（合成器）从种子实体出发，以 ReAct 方式迭代 search+browse，自主构建信息空间，并由模型自己决定何时停止、自己合成一个需要跨多网站串联的初始 QA。

作者给了一个非常直观的例子：种子 "Brazil National Team"（巴西国家队），经过 1950 年世界杯→裁判 George Reader→Southampton 俱乐部→1976 年足总杯→Bobby Stokes 这样一串多跳串联，「（推断）」最终合成出一道需要多次跨网站跳转才能回答、且没有任何单页能直接命中的问题。这正是长程 agent 要面对的典型挑战。

关键设计差异在于：相比 graph-based 方法，作者放弃了显式图结构。「（推断）」这样做的代价是失去了对信息空间的显式控制，但换来了实现简洁——不需要节点/边的选择启发式，只需要一个足够强的模型和一个 prompt。而"模型自行决定何时停止"这一设计，让合成过程天然地贴近 agent 真实探索的形态，产出的轨迹（探索路径）本身也可以复用。

2.4 Iterative Query Evolution（§2.3，核心创新点二："长到短"进化）

这是全文最具反直觉的一处。既有 evolution 路线是 short-to-long（不断注入新信息、把 query 越写越长）；作者反其道而行，做 long-to-short——在一个已经可解但"线索太露骨"的问题上，通过删减让问题变难，同时保持答案不变（§4 式 3，每轮进化继续补充探索信息空间）。

具体的删减手段有三类（§4）：

  1. 移除显著线索：把题干里一眼就能照抄的提示词删掉。
  2. 对日期/地点/专名做模糊化：把具体的年份、地点、人名替换成更模糊的表述。
  3. 用替代描述替换显式引用：这是最有代表性的一条。例如把 "Manchester United" 改写成 "First Division giant"（"甲级联赛巨人"），让模型必须靠语义理解而非字符串匹配来锁定那个实体。

「（推断）」这套进化的核心洞察是：问题的难，往往不是信息不够，而是线索太顺。人出的难问题之所以难，是因为它把关键信息的"入口"藏起来了；作者用这三类删减精准地把"入口"挖掉，从而在不大幅改动题目语义的前提下逼出难度。合成 prompt 以 BrowseComp-en 的三条 exemplar 为范例，「（推断）」这使得合成出的问题天然对齐 BrowseComp 的文体与难度基调制。

2.5 WebExplorer-QA 数据集（§2.4）

经过 5 轮 evolution，作者得到约 40K 的 evolved QA 对。这个数据集有两个特征值得强调（结合 §3 Table 1、§5 Figure 4）：

  • 难度被量级化：同样用 Claude-4-Sonnet 解答，初始 QA（Initial）的正确率是 86.6%，而进化后（Evolved）降到 67.1%；平均轮数从 7.9 升至 9.9。这意味着数据集的难度得到了实打实的提升，而不是嘴上说说。
  • 分布逼近真实基准：进化后，4 turns 内易解样本的比例显著下降（Figure 4 左），Evolved QA 的 turns 分布已逼近 BrowseComp-en（Figure 4 右）。

2.6 训练配方（§3：Cold Start and Reinforcement Learning）

SFT 冷启动（§3.1）：用商业模型做 rejection sampling，只保留正确轨迹做监督微调。格式为 ReAct 格式，带 / / 标签。配置约 13K 样本、bs 32、lr 1e-5、4 epochs（§4.1 Training Details）。这一步的作用「（推断）」是让模型先学会"怎么走"（动作格式、工具调用、路径规划的基本套路），为后续 RL 提供一个不崩的起点。

RL（§3.2）：采用 GRPO。与 SFT 不同，RL 直接"用合成 QA、不需要轨迹示范"（即直接给出难问题，让模型自己探索，不预置标准轨迹）。奖励函数为（式 4）：

`

R = 0.2 · R_format + R_correct

`

其中 R_format 保证输出结构正确，R_correct 由 DeepSeek-V3 作为 LLM-as-Judge 判定答案是否正确（权重 0.2 的格式奖励是为了防止 collapse）。配置约 12K 样本、group 8 rollouts、bs 64、lr 1e-6（§3.2/§4.1）。最值得注意的是 上下文渐进扩展 设计：64K/50 turns → 96K/75 turns → 128K/100 turns。「（推断）」这模仿了训练后期不断"放宽天花板"的思路——先让模型在较短的轨迹里稳定、再逐步放开让它走更远，避免一开始就面对超长轨迹而中途崩溃。

2.7 WebExplorer-8B 模型

把上述数据与训练配方应用到 Qwen3-8B 上，得到最终模型 WebExplorer-8B。作者明确其定位是"低成本长程 web agent 的可行路径"，且全部评测统一在一套 (search/browse) scaffold 下完成（§6）。这一点极其关键——它意味着跨方法、跨模型的对比是在同一把尺子上量的，「（推断）」这让 WebExplorer-8B 的成绩具有了较强的可比性。

三、方法拆解（How / 具体怎么做，以及为什么这么做）

3.1 整体管线逻辑

把全文流程串联起来，WebExplorer 的完整管线如下：

`

Wikipedia 种子实体

│

▼

[Model-Based Exploration] 强 LLM 以 ReAct 迭代 search+browse

│ 模型自行决定何时停止，合成跨多网站初始 QA

▼

[Iterative Query Evolution] 长到短，删减线索/模糊化/替换引用（答案不变）

▼

│

├──► [SFT 冷启动] rejection sampling，只留正确轨迹，约 13K 样本

│

▼

[RL / GRPO] 约 12K 样本，DeepSeek-V3 judge，渐进扩展上下文

▼

WebExplorer-8B（Qwen3-8B）

`

3.2 为何"模型自主探索"优于"显式构图"

作者选择放弃图构建，这一取舍值得从成本与收益两面拆（§4 对比）：

  • 对 graph-based 的批评：WebSailor/WebShaper 需要显式建图，节点扩展与选择启发式复杂。复杂度是真实的工程负担——「（推断）」图结构设计、节点打分、子图选择、图到 QA 映射，任何一环都需要额外调参，且这些启发式往往依赖领域知识，难以迁移。
  • WebExplorer 的替代：只用一个 prompt + 一个强 LLM。信息空间不是被"构建"出来，而是被模型"走"出来的。「（推断）」这种做法的最大优势是 自然——探索路径本身就是模型真实行动的结果，不像图构建那样需要人为设定"哪些节点之间该连边"。
  • 代价：失去显式可控性。「（推断）」模型走偏了、停早了、合成了烂问题，作者无法像图方法那样从结构上定位问题；只能靠大量生成 + 过滤（rejection sampling、judge）兜底。

3.3 "长到短"进化的三个删减维度拆开看

作者的三类删减，本质上是在三个不同的信息暴露程度上做减法：

删减类别对什么做减法举例对模型的挑战
------------
移除显著线索显式、可字面匹配的提示删掉题干里照抄就能答的词需要推理而非检索
模糊化日期/地点/专名具体的指称信息年份、地名、人名变模糊需要时间/地理/本体知识补齐
替代描述替换显式引用可直接命中的实体名Manchester United → First Division giant需要语义理解对齐实体

「（推断）」这是一个非常漂亮的"难度控制"分解——它把"如何让问题变难"拆成了可独立操作、可解释、可量化的三个旋钮，而非笼统地"把 query 写复杂"。而且答案不变这一约束保证了难度提升不是靠换问题，而是靠把同一个问题的入口封死。

3.4 SFT 与 RL 的分工，以及"无需轨迹示范"的意义

作者在训练上的一个微妙但重要设计是：SFT 需要轨迹（rejection sampling 保正确轨迹），RL 则"直接用合成 QA、无需轨迹示范"（§3.2）。

「（推断）」背后的逻辑值得解读：

  • SFT 阶段模型还没学会走路，必须给它正确的"示范"（哪些轨迹走对了），否则冷启动会崩。
  • RL 阶段模型已经过了冷启动，此时真正的提升来源是"自己摸索"，所以不需要再给定标准轨迹——给定反而会限制它的探索。GRPO 天然适合这种"只给问题、不给答案路径"的设定：模型自己 rollout 一组答案，内部做偏好比较。
  • 奖励里 0.2 权重的 R_format 是个精妙设计。「（推断）」纯 accuracy 奖励容易让模型钻空子（格式乱但 judge 恰好判对），加一个格式奖励可以稳定输出结构，防止训练过程中模型把结构"忘了"。

3.5 上下文渐进扩展（64K→96K→128K）的工程含义

这是 §3.2 里最容易被忽视、但对长程 agent 至关重要的工程细节。轨迹长度 >40K tokens、平均 tool calls 从约 11 升到 16+（Figure 5），这已经远超常规 LLM 的训练上下文。作者没有一次性上 128K，而是分三档渐进放开：

  • 64K/50 turns → 96K/75 turns → 128K/100 turns

「（推断）」动机很直观：如果在训练一开始就要求模型在 100 turns 里稳定、无崩溃地走完，模型大概率会早崩或严重退化；渐进放开让模型先在较短的范围内形成稳定的长程规划能力，再逐步拉伸。这与数学 RL 里"先学短 CoT、再延长 CoT"的思路一致，作者在 §4.2 也明确把这一动力学类比为单轮数学 RL 的 long CoT 涌现。

3.6 评测口径的严谨性（Avg@4 + 统一 scaffold）

作者在 §4.1/§5 反复强调两点评测纪律，这直接决定了结论的可信度：

  1. 统一 scaffold：所有对比模型都在同一套 search/browse scaffold 下评测。「（推断）」这一点排除了"工具差异带来的成绩差异"，让 BrowseComp 上的对比真正做到同题同秤。
  2. Avg@4 + LLM-as-Judge：所有分数都是取 4 次采样平均值，且由 LLM（DeepSeek-V3）判分。「（推断）」Avg@4 降低了单次采样噪音；GAIA 采用 103 样本 text-only 验证子集（沿用 WebShaper 口径），保证了与既有工作的口径一致。

「（推断）」需要提醒的是，LLM-as-Judge（而非人工核验）是这套评测的相对薄弱环节——判分模型本身的偏差会被带入所有分数，这一点在本文的批判部分还会展开。

结语

WebExplorer 的价值不在其模型本身（8B 终究是 8B），而在其揭示的一条路径：用"强者自主探索 + 反向删减进化"造出接近真实难度的长程数据，再用 SFT+GRPO 把它训练成一个便宜但能干的长程 web agent。它最大的贡献是为 web agent 的数据合成提供了一个"去复杂化"的替代方案——不要图，只要一个能走得很远的探索者；同时用 RL 动力学证据（tool calls 与分数同步增长）为"长程 agentic search 可由 RL 扩展"提供了统一 scaffold 下的实证支撑。其代价与局限同样清晰：难度尚未对齐 BrowseComp、语料偏单一、评测依赖 LLM-as-Judge、训练成本并不低。这些恰恰是后继工作最有戏的切入点。
