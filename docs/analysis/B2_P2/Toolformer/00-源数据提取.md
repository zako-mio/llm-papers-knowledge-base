## §4 方法细节

- **API 线性化**：e(c) = `<API> ac(ic) </API>`；e(c, r) = `<API> ac(ic) →r </API>`，用特殊 token `<API>`、`</API>`、`→`。实践中用 " [", "]", "->" 避免改动现有 LM 词表。
- **三步骤生成 C∗**（Figure 2）：
  1. **采样 API 调用**：为每工具写 prompt P(x)（如 Figure 3 QA prompt）。对每个位置 i 计算 p_i = pM(`<API>` | P(x), x1:i-1)，保留 p_i > τ_s 的位置（超 k 个只取 top k），对每位置采样至多 m 个调用 c^i。
  2. **执行 API 调用**：获得单文本序列响应 r。
  3. **过滤 API 调用**：定义加权交叉熵 L_i(z) = -Σ_{j=i}^{n} w_{j-i} · log pM(x_j | z, x1:j-1)。比较 L+_i = L_i(e(c_i, r_i)) 与 L-_i = min(L_i(ε), L_i(e(c_i, ε)))。保留 L-_i - L+_i ≥ τ_f 的调用（即加 API 及结果至少降低损失 τ_f）。
- **模型微调**：将保留调用与原文交错，x∗ = x1:i-1, e(c_i, r_i), xi:n；用标准语言建模目标微调 M。C∗ 含与 C 完全相同文本，仅穿插 API 调用，故不改变内容分布。
- **推理**：正常解码直到生成 "→" token → 中断解码 → 调用对应 API → 插入响应与 `</API>` 后继续解码。
- **五个工具具体实现**：问答用 Atlas（检索增强，微调于 Natural Questions）；计算器仅四则基本运算，结果四舍五入两位小数；Wikipedia 搜索用 BM25 检索 KILT 的 Wikipedia dump；翻译用 600M NLLB（200 语言，fastText 检测源语言，目标英语）；日历返回当前日期（无输入）。
- **数据集启发式**：为省算力，对文本子集限定（如计算器仅处理含至少 3 个数字的文本）。权重函数 w~t = max(0, 1-0.2·t) 归一化，促使 API 调用靠近信息真正有用的位置。τ_s、τ_f 各工具单独选取。
- **解码**：不只在 `<API>` 是最可能 token 时开始调用，而是当它在 top-k（用 k=10）时开始；每次输入至多一次 API 调用以防死循环。
- **基线**：GPT-J（无微调）、GPT-J+CC（无 API 微调于 C）、Toolformer、Toolformer(disabled)（解码时禁用 API，即 p(`<API>`) 置 0），另对比 OPT(66B)、GPT-3(175B)。

## §5 实验结果要点

- **§4.2 下游任务（零样本提示）**：
  - **LAMA**（SQuAD/Google-RE/T-REx）：Toolformer 33.8/11.5/53.5，较同尺寸 best baseline 提升 11.7/5.2/18.6 点，也优于 OPT(66B) 与 GPT-3(175B)，主要靠问答工具（98.1%）。
  - **数学**（ASDiv/SVAMP/MAWPS）：Toolformer 40.4/29.4/44.0，远超 OPT/GPT-3，靠计算器（97.9%）；即使禁用 API 也有提升（微调自增数学能力）。
  - **QA**（WebQS/NQ/TriviaQA）：Toolformer 26.3/17.7/48.8 远超同尺寸基线，但落后 GPT-3(175B)，多靠 Wikipedia 搜索（99.3%）；因搜索器简单无法交互改进。
  - **MLQA**：翻译工具使用 63.8%-94.9%（Hindi 例外 7.3%），Toolformer 未稳定优于 GPT-J——部分语言上 CCNet 微调反而劣化（分布偏移）；OPT/GPT-3 因不解题而不给英语答案而表现极弱。
  - **时间数据集**：TEMPLAMA 16.3（日历仅 0.2%，提升主要来自搜索/问答工具）；DATESET 27.3（日历 54.8%，提升全归功日历）。
- **§4.3 语言建模**：微调于 C∗ 在禁用 API 时困惑度与微调于 C 相同（WikiText 10.3 / CCNet 10.5），未破坏建模能力。
- **§4.4 缩放律**：工具使用能力在约 775M 参数处涌现；更小模型用与不用工具结果相似；大模型用工具收益增大，用/不用 API 的差距仍大。
- **§5 分析**：增大 k 使更多例做 API 调用（T-REx 40.3%→98.1%，WebQS 8.5%→100%）；k=1 时模型有校准——选不会时调用（其用 API 子集 44.3/19.9 高于无 API 平均 34.9/18.9）。数据质量：高 L-_i - L+_i 对应有用调用；少量噪声调用反而防止模型盲从每次结果。

## §6 局限（§7 Limitations）

- 无法**链式**使用工具（一个工具的输出作为另一工具的输入），因各工具调用独立生成、训练数据无链式示例。
- 无法**交互式**使用工具——尤其对搜索结果，无法浏览多条结果或改写查询（对比 Nakano 2021）。
- 对输入措辞敏感：是否调用 API 易受 prompt 精确措辞影响。
- 样本效率低：例如处理超百万文档仅得数千个有用计算器调用；可迭代应用缓解。
- 调用 API 时未考虑工具依赖的计算成本。
