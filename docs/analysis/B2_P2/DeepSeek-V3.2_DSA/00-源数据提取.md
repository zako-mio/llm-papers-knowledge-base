## §4 方法细节
### 4.1 DSA 架构（§2.1，p3–4）
- **Lightning Indexer**：索引分数 `I_{t,s} = Σ_{j=1}^{H_I} w_{t,j}^I · ReLU(q_{t,j}^I · k_s^I)`；q/w 由 query token 派生，k 由前序 token 派生；选 ReLU 纯为吞吐；head 数少且可 FP8 实现。
- **细粒度 token 选择**：按 top-k 索引分取 KV 条目，`u_t = Attn(h_t, {c_s | I_{t,s} ∈ Top-k})`——token 级精确选择（区别于块级）。
- **MLA 实例化**：基于 MLA 的 MQA 模式——每个 latent 向量（MLA 的 KV 条目）被该 query token 的所有 query head 共享，满足内核级 KV 复用要求（引 NSA, Yuan et al. 2025）。
- **短序列优化**：短序列 prefill 用 masked MHA 模式模拟 DSA 以获得更高效率（p5 §2.3）。

### 4.2 稀疏化续训两阶段（§2.1.1，p3–4）
起点为已扩至 128K 的 V3.1-Terminus checkpoint，数据分布与其 128K 长上下文扩展数据完全一致：
1. **Dense Warm-up**：冻结除 indexer 外全部参数，保持 dense attention；用主注意力跨头求和后 L1 归一化作为目标分布，KL 散度损失对齐（式 3）；lr 1e-3，仅 1000 步（共 2.1B tokens）；
2. **Sparse Training**：启用 top-k=2048 选择机制，全参数适配稀疏模式；indexer 继续做 KL 对齐但只在选中集合 S_t 上（式 4）；**indexer 输入从计算图 detach**——indexer 仅由 KL 损失训练、主模型仅由 LM loss 训练；lr 7.3e-6，15000 步（共 943.7B tokens）。post-training 同样全程使用稀疏注意力。

### 4.3 Scaling GRPO 的四项稳定技术（§3.1，p7–8）
1. **Unbiased KL Estimate**：修正 K3 estimator，经当前/old 策略重要性比校正后 KL 梯度无偏；原 K3 在 π_θ≪π_ref 时给低概率 token 无界放大的提升权重→噪声梯度累积致不稳；实践上数学等域弱 KL 或免 KL 更优。
2. **Off-Policy Sequence Masking**：rollout 大批拆多 mini-batch 更新 + 训推框架差异双重 off-policy 源；对 A<0 且采样策略与当前策略平均 log-ratio>δ 的负序列整体 mask；π_old 直取推理框架返回概率（同时覆盖两源）；直觉=模型最应从自己的错误学习，而高度 off-policy 的负样本有害。
3. **KeepRouting**：MoE 训推路由不一致会引发激活子空间突变；训练期强制复用采样期的专家路由路径（自 DeepSeek-V3-0324 起 pipeline 标配）。
4. **KeepSamplingMask**：把采样期 top-p/top-k 截断 mask 保留到训练期，使新旧策略动作空间一致（修复重要性采样前提破坏）；与 top-p 组合可有效维持 RL 中语言一致性。

### 4.4 工具调用中的思考管理（§3.2，p9–12）
- **Context Management 规则**：仅在**新 user 消息**进入时丢弃历史推理内容；仅追加 tool 输出则完整保留推理链；丢弃推理时保留工具调用与结果历史。RooCode/Terminus 类以 user 消息模拟工具交互的框架无法受益，官方建议此类场景用 non-thinking 模型。
- **冷启动**：用 system prompt 指示模型在推理过程中内嵌多次工具调用，偶尔产出目标轨迹作为 RL 种子。
- **四类 Agent 管线**（Table 1，p10）：
  - *Search Agent*（50,275，真实环境/合成 prompt）：长尾实体采样→出题 agent 可控深度广度探索→异构多答 agent→带搜索的验证 agent 多轮校验，仅保留"标准答案正确且所有候选可证错误"样本；再补 GenRM rubrics 评分兼顾有用性。
  - *Code Agent*（24,667，真实环境/抽取 prompt）：数百万 GitHub issue-PR 对启发式+LLM 过滤；自动环境搭建 agent 处理装包/依赖/测试；JUnit 统一输出；**gold patch 须 F2P>0 且 P2F=0** 方准入库；产出数万可复现环境，覆盖 Python/Java/JS/TS/C/C++/Go/PHP。
  - *Code Interpreter*（5,908，真实环境/抽取 prompt）：Jupyter Notebook 求解数学/逻辑/数据科学题。
  - *General Agent*（4,417，全合成）：自动环境合成 agent 迭代生成"<environment, tools, task, verifier>"四元组，设计原则"**难解易验**"（solution function 只能经工具接口访问数据库、必须过 verification function、逐步加难度、不足则扩工具集）；RL 后仅留 pass@100>0 实例得 1,827 环境。

### 4.5 专家蒸馏 + 混合 RL（p5–6）
六个专家域（数学/编程/通用逻辑推理/通用 agentic/agentic coding/agentic search，均支持 thinking 与 non-thinking 双模式），各自从同一 base checkpoint 大规模 RL；专家产出蒸馏数据，最终 checkpoint 用蒸馏数据训练（仅略低于专家，RL 后差距消除）。RL 采用 GRPO 单阶段合并 reasoning+agent+human alignment，规避多阶段灾难性遗忘。Speciale 变体：仅推理数据 + 降低长度惩罚 + 引入 DeepSeekMath-V2 数据/奖励。

## §5 实验结果要点
- **评测设置**（p13）：温度 1.0、上下文 128K、工具类基准 thinking 模式函数调用格式；MCP-Universe/MCP-Mark 用内部环境；HLE 官方模板下 V3.2-Thinking 得 23.9（自报模板 25.1）。
- **主对照（Table 2，p13）**：英文知识 MMLU-Pro 85.0/GPQA-Diamond 82.4/HLE 25.1；代码 LiveCodeBench 83.3/Codeforces 2386；数学 AIME25 93.1/HMMT-Feb 92.5/HMMT-Nov 90.2/IMO-AB 78.3；Code Agent TerminalBench2.0 46.4（ClaudeCode 框架；Terminus non-thinking 仅 39.3）、SWE-Verified 73.1（跨框架鲁棒区间 72–74）、SWE-Multilingual 70.2；Search BrowseComp 51.4（context mgmt 后 67.6*）、BrowseCompZh 65.0；Tool Use τ-bench 80.3（Airline 63.8/Retail 81.1/Telecom 96.2）、MCP-Universe 45.9、MCP-Mark 38.0、Tool-Decathlon 35.2。
- **Token 效率（Table 3，p15）**：V3.2-Thinking 平均输出 token 显著低于 K2-Thinking（如 AIME25 16k vs 24k、IMO-AB 27k vs 37k）取得相当精度；Speciale 则相反地以更多 token（77k @ Codeforces）换更高峰值精度。
- **Speciale 峰值能力（Table 4，p15）**：IMO2025 35/42、CMO2025 102/126、IOI2025 492/600（第 10）、ICPCWF2025 10/12（第 2），全部金牌档。
- **合成任务双消融（§4.3，p15 + Figure 5）**：难度——50 个抽样任务 V3.2-Exp 12% vs 闭源最好 62%；泛化——在 SFT checkpoint 上仅用合成 agentic 数据做 non-thinking RL，即可见对下游/真实环境的显著迁移提升，且评测所用环境与工具集均未在 RL 中出现（out-of-domain 泛化证据）。
- **成本（Figure 3，p6）**：H800 集群实测（$2/GPU·小时），prefill 与 decode 每 token 成本随位置增长显著低于 V3.1-Terminus（decode 128K 处约 $0.1 vs $0.4/百万 token 量级，见图）。

## §6 局限（原文可证 + 明显边界）
1. **上下文上限 128K 偏紧**：约 **20%+ 的 BrowseComp 测试样例超出 128K**，需 context management 补救才有 67.6*（裸分 51.4）（p14 §4.1）。
2. **冗余自我验证行为**：频繁生成过长验证轨迹，MCP-Mark GitHub/Playwright 等任务常撑爆 128K 限窗直接拖累得分（作者列为 future work 与用户实用注意事项，p14）。
3. **Token 效率不及闭源旗舰**：Speciale 精度虽超 Gemini-3.0-Pro 但 token 效率"仍显著劣于"对方；正式版以更严 token 约束换部署成本，承认 token 效率是未来关键方向（p14–15）。
4. **框架兼容性问题**：thinking 模式的 context management 与 Terminus 不兼容（TerminalBench 46.4 须换 ClaudeCode 框架取得；Terminus 下 non-thinking 仅 39.3）；RooCode 类框架亦无法受益于思考保留机制（p9、p14）。
5. **DSA 性能为"无损近似"而非增益**：架构改动目标是 parity（Elo 接近、基准相当），长上下文收益主要体现为效率而非质量；部分独立长上下文评测（AA-LCR +4）属外部佐证且幅度有限。
6. **合成环境的模拟鸿沟**：General Agent 环境全合成（沙盒数据库+自造工具），论文自证其难度但对"真实世界工具分布"的覆盖依赖 out-of-domain 泛化检验，未见真实用户流量回归证据；search/code 任务 prompt 亦非来自真实用户交互（p10 §3.2.3 自述）。
