# DeepSeek-V3.2 深度解读：DSA 稀疏注意力与规模化 Agentic RL 的工程化合流

> **数据依据声明**：本报告全部事实性数字以同目录《00-源数据提取.md》为唯一依据，未在源数据中出现的技术判断、因果解释与外推均在行文中明确标注「（推断）」。

## 摘要

DeepSeek-V3.2（arXiv:2512.02556，2025-12-02，23 页）是 DeepSeek-AI 的开源旗舰模型，相对上一版 V3.1-Terminus 的**唯一架构改动**是通过继续训练引入 DeepSeek Sparse Attention（DSA），将核心注意力复杂度从 **O(L²) 降至 O(Lk)**（实验取 k=2048），经「dense warm-up（2.1B tokens）→ sparse training（943.7B tokens）」两阶段完成稀疏化适配，达成与 dense 版本的性能 parity（ChatbotArena Elo 接近、标准基准相当），并显著压缩长上下文推理成本。后训练侧，论文以六域专家蒸馏 + **GRPO 单阶段混合 RL** 合并推理、agentic 与人类对齐三目标，提出无偏 KL 估计、Off-Policy 序列掩码、KeepRouting、KeepSamplingMask 四项稳定性技术，支撑 1,800+ 环境、85,000+ 复杂 prompt 的四类 agent 数据管线规模化训练，使「thinking 内嵌工具调用」成为原生能力。V3.2-Thinking 在 AIME2025 得 93.1、SWE-Verified 73.1、BrowseComp 51.4（context management 后 67.6*）；Speciale 变体 AIME25 达 96.0、IMO2025 取 35/42 金牌，但 token 效率仍显著逊于 Gemini-3.0-Pro，128K 上下文偏紧与冗余自我验证构成主要边界。本文按问题定位—概念内核—方法拆解—证据链—批判分析—启示影响六段展开。

## 一、问题定位

### 1.1 三大缺陷诊断：差距为何重新拉开

论文 Introduction（p1–2）开宗明义：开源与闭源模型的差距正在拉大，根源被归结为三个层面。第一是**架构效率**——主流 Transformer 的 dense attention 复杂度为 O(L²)，当上下文扩展到 128K 量级时，注意力的计算与访存成本成为推理经济的瓶颈；第二是 **post-training 算力**——论文给出一个关键观察：post-training 的算力投入**已超过预训练成本的 10%**，且性能随 RL 预算持续提升（p13 §4.1；p2 §1），这意味着能力增长的重心正从预训练向 RL 后训练迁移，算力分配策略本身成为竞争力变量；第三是 **agent 泛化**——真实场景中的工具使用、搜索、编码 agent 需要「环境规模 × 任务质量 × RL 稳定性」三位一体的系统工程，而非单一算法突破。

这三个缺陷并非并列关系（推断）：架构效率决定了单位 token 的服务成本下限，post-training 决定了能力的上限增速，agent 泛化则决定了能力能否兑换为商业价值。V3.2 的整体设计可以理解为对这三个缺陷的一次同时回应——DSA 回应第一条，Scaling GRPO 四项技术回应第二条，四类 agent 管线与 thinking in tool-use 回应第三条。

### 1.2 为什么把注意力稀疏化作为架构突破口

（推断）Agent 时代的负载结构与聊天时代根本不同：搜索结果页、代码仓库、工具返回的 JSON、多轮环境观测，都以超长上下文形式涌入模型。若注意力成本维持 O(L²)，则 agent 任务的单位成本无法降到经济区间，「能力可用」与「成本可用」之间会始终隔着一道鸿沟。因此架构改动的优先级不是提升质量，而是**在不损质量的前提下压扁成本曲线**——这也解释了论文为何把 DSA 的验收标准设定为 parity 而非增益。

### 1.3 问题定义的克制性

值得注意的是，论文对 DSA 的定位极为克制：目标是「与 dense attention 性能相当」（§2.2 Parity Evaluation），长上下文收益主要体现在效率而非质量上；独立评测中 AA-LCR 高出 4 分（reasoning mode）、Fiction.liveBench 多指标胜出属于外部佐证且幅度有限（源数据 §6.5）。这种「无损近似」的目标函数选择，反映了一种成熟的工程价值观：架构激进换血的风险由全社区承担，而渐进改造的红利可以直接兑现。

## 二、概念内核

### 2.1 DSA：lightning indexer + 细粒度 token 选择

DSA 的核心思想是「先用便宜的打分器找出值得注意的 token，再只在选中集合上做完整注意力」。它由两个组件构成：

其一，**Lightning Indexer**。对 query 位置 t 与前序位置 s，索引分数定义为 `I_{t,s} = Σ_{j=1}^{H_I} w_{t,j}^I · ReLU(q_{t,j}^I · k_s^I)`。其中 q 与权重 w 由 query token 派生，k 由前序 token 派生。两个实现细节颇具代表性：激活函数选用 ReLU **纯为吞吐考虑**；head 数少且可全程 FP8 实现（§2.1，p3–4）。这使 indexer 虽然形式上仍是 O(L²) 的全序列扫描，但计算量远小于 MLA 主注意力，构成「便宜的第一遍」。

其二，**细粒度 token 选择**。按 top-k 索引分逐条选取 KV 条目，`u_t = Attn(h_t, {c_s | I_{t,s} ∈ Top-k})`。与 NSA 的块级选择相比，这是 **token 级精确选择**（引 NSA, Yuan et al. 2025），理论上能在同等预算下保留更相关的信息（推断：粒度收益的具体幅度论文未单独消融，此为机制层面的合理推断）。

### 2.2 MLA(MQA 模式) 实例化：KV 复用的工程闭环

DSA 基于 MLA 的 MQA 模式实例化：MLA 的 KV 条目即 latent 向量，每个 latent 向量被该 query token 的**所有 query head 共享**，从而满足内核级 KV 复用要求。这一设计保住了 MLA 家族原有的缓存优势——稀疏化发生在「读取多少」的维度，而不动「存什么」的维度（推断：这正是 DSA 能以续训而非从头训练方式落地的结构性原因之一）。

### 2.3 复杂度账本与短序列兜底

综合来看，V3.2 的注意力成本账本是：主注意力从 O(L²) 降至 **O(Lk)**（k≪L，实验 k=2048）；indexer 保持 O(L²) 但常数极小（head 少、FP8、ReLU 吞吐友好）。此外还有一个常被忽略的细节：**短序列 prefill 用 masked MHA 模式模拟 DSA 以获得更高效率**（p5 §2.3）——当 L 本身不大时，稀疏选择的调度开销可能超过收益，直接走稠密路径反而更快。这种「长短双模式」的务实处理是生产级系统的标志（推断：该切换对用户透明，具体阈值未披露）。

### 2.4 Thinking in Tool-Use：推理链作为一等公民

传统 tool-use 把推理与调用视为交替步骤，而 V3.2 提出**在推理过程内部嵌入多次工具调用**：模型在一条思维链的中途发起工具请求，拿到结果后继续推理。配套的 Context Management 规则规定：仅在**新 user 消息**进入时丢弃历史推理内容；仅追加 tool 输出则完整保留推理链；丢弃推理时仍保留工具调用与结果历史。这一规则组成了「长程 agent 会话的记忆经济学」（详见三、四节）。

### 2.5 Speciale：以 token 换精度的峰值变体

Speciale 是 V3.2 的竞赛特化变体：仅用推理数据训练、降低长度惩罚、引入 DeepSeekMath-V2 的数据与奖励。它与正式版构成一对刻意设计的张力点——正式版追求「更少 token 下够用的精度」，Speciale 反其道而行，用 77k 输出 token 在 Codeforces 换取更高峰值精度。二者共同勾勒了同一基座上的「效率-精度前沿」。

## 三、方法拆解

### 3.1 两阶段稀疏化续训：如何让 671B 级模型无痛换注意力

整个流程的起点是**已扩展到 128K 上下文的 V3.1-Terminus checkpoint**，续训数据分布与其 128K 长上下文扩展数据完全一致——最大限度消除分布漂移变量。

**阶段一：Dense Warm-up（2.1B tokens）**。冻结除 indexer 外的全部参数，模型保持 dense attention 运行；以主注意力跨 head 求和后做 L1 归一化得到的分布作为目标，用 KL 散度损失训练 indexer 对齐（式 3）。学习率 1e-3，仅 1000 步（1000 步 × 16 序列 × 128K = 2.1B tokens）。此阶段的本质是「让 indexer 在 dense 教师监督下学会打分」，而主模型毫发无损（推断：这保证了冷启动阶段服务指标零回退，是一种可随时中断的安全设计）。

**阶段二：Sparse Training（943.7B tokens）**。启用 top-k=2048 选择机制，全参数适配稀疏模式；indexer 继续 KL 对齐但只在被选中的集合 S_t 上计算（式 4）。关键的解耦设计在此出现：**indexer 输入从计算图中 detach**——indexer 仅由 KL 损失训练，主模型仅由语言建模损失训练。学习率降到 7.3e-6，15000 步 × 480 序列 × 128K = 943.7B tokens。此后 post-training 全程使用稀疏注意力。

Detach 的意义值得展开（推断）：若允许主任务的梯度流入 indexer，indexer 可能学出「配合主模型偷懒」的退化打分（例如系统性跳过难样本），导致稀疏集合质量静默劣化；切断梯度后，indexer 的优化目标始终锚定 dense 分布这一外部真值，主模型只能在给定选择下尽力拟合——职责边界清晰，故障域隔离。

### 3.2 Scaling GRPO：四项稳定性技术的机制解剖

**（1）Unbiased KL Estimate。** 标准 K3 estimator 在 π_θ ≪ π_ref 时会给低概率 token 无界放大的提升权重，噪声梯度累积导致训练不稳。修正方案是经当前策略/old 策略的重要性比校正，使 KL 梯度无偏。实践层面的推论同样重要：在数学等领域，弱 KL 甚至免 KL 更优——正则化的代价在强推理任务上可能高于其稳定收益。

**（2）Off-Policy Sequence Masking。** 大规模 RL 中 off-policy 有两个来源：rollout 大批量拆分为多个 mini-batch 更新造成的陈旧性，以及训练/推理两套框架数值实现的差异。处理办法是对优势 A<0 且采样策略与当前策略平均 log-ratio 超过阈值 δ 的负序列**整条掩掉**；π_old 直接取推理框架返回的概率，一次性覆盖两个 off-policy 源。其直觉表述非常精彩：「模型最应从自己的错误中学习」，高度 off-policy 的负样本对应的已经不是当前策略的行为，惩罚它们只会引入方差。

**（3）KeepRouting。** MoE 架构下训练期与推理期的专家路由不一致会引发激活子空间突变。修复方式朴素而有效：训练期强制复用采样期的专家路由路径。源数据注明该做法自 DeepSeek-V3-0324 起已是 pipeline 标配。

**（4）KeepSamplingMask。** 采样期的 top-p/top-k 截断 mask 若不在训练期保留，会破坏重要性采样的前提（新旧策略动作空间不一致）。将该 mask 保留到训练期即可修复；与 top-p 组合还能有效维持 RL 过程中的语言一致性（防止 RL 调优导致语言风格漂移崩溃）。

四项技术合起来看（推断），分别对应 RLHF 大规模化的四类经典崩塌模式：梯度噪声、off-policy 方差、MoE 不一致性、动作空间漂移。它们的共同特征是「工程修补而非算法发明」，可复制性强，是这份技术报告对开源 RL 社区最有公共价值的部分之一。

### 3.3 四类 Agent 数据管线：85,000 条轨迹的质量工艺

总盘子：**1,800+ 环境、85,000+ 复杂 prompt**（Table 1，p10），按管线拆分为 search 50,275、code 24,667、interpreter 5,908、general 4,417。每条管线的质量控制各有侧重：

**Search Agent（50,275）**：长尾实体采样保证题目多样性 → 出题 agent 可控深度广度地探索 → 异构多答 agent 生成候选 → 带搜索引擎的验证 agent 多轮校验，最终只保留「标准答案正确且所有候选项均可证伪」的样本；再补 GenRM rubrics 评分兼顾有用性。这是一个以「可证伪性」为核心的对抗式提纯流水线。

**Code Agent（24,667）**：以数百万 GitHub issue-PR 对启发式召回 + LLM 过滤；自动环境搭建 agent 处理装包、依赖、测试运行，JUnit 统一输出格式；入库硬门槛是 **gold patch 必须 F2P>0 且 P2F=0**（能修复失败测试、不破坏通过测试）。最终产出数万可复现环境，覆盖 Python/Java/JS/TS/C/C++/Go/PHP 七种语言。

**Code Interpreter（5,908）**：Jupyter Notebook 环境求解数学、逻辑与数据科学题，形态相对轻量。

**General Agent（4,417，全合成）**：自动环境合成 agent 迭代生成 `<environment, tools, task, verifier>` 四元组，设计原则凝练为四个字——**「难解易验」**：solution function 只能经由工具接口访问数据库、必须通过 verification function 校验、逐步提高难度、难度不足则扩充工具集。RL 之后仅保留 pass@100>0 的实例，得 1,827 个环境。「pass@100>0」的过滤逻辑保证了任务处于能力边缘的可学习区间——全对的任务没有梯度，全错的任务没有信号（推断：这是一种隐式的课程学习机制）。

### 3.4 冷启动与思考管理

冷启动阶段用 system prompt 指示模型在推理过程中内嵌多次工具调用，偶尔产出目标轨迹作为后续 RL 的种子数据。Context Management 的丢弃规则（见 2.4 节）则在部署端与之呼应。论文特别指出：RooCode/Terminus 这类以 user 消息模拟工具交互的框架无法受益于思考保留机制，官方建议此类场景使用 non-thinking 模型——这条建议实际上划清了「框架协议兼容性」的适用边界（详见五节批判）。

### 3.5 专家蒸馏 + 单阶段混合 RL

训练拓扑上，六个专家域（数学、编程、通用逻辑推理、通用 agentic、agentic coding、agentic search，均支持 thinking 与 non-thinking 双模式）各自从同一 base checkpoint 出发做大规模 RL；专家模型随后产出蒸馏数据，最终 checkpoint 用蒸馏数据训练，性能仅略低于专家，且经过 RL 后差距消除。最终的偏好对齐不走多阶段串联，而是 **GRPO 单阶段合并 reasoning + agent + human alignment** 三个目标，规避多阶段训练固有的灾难性遗忘。

（推断）「专家探索 → 蒸馏回收 → 单阶段合并」本质上是用并行专家换取探索多样性，再用蒸馏把多样性收敛回单一模型，最后用单阶段 RL 避免目标串行冲突。它牺牲了少量专家峰值，换来了训练管线的简洁与稳定性，与 Speciale「另起炉灶冲峰值」形成完整的策略光谱。

## 四、证据链

### 4.1 Parity 证据（§2.2，p5）

三层证据：标准基准上与 V3.1-Terminus 性能相当；ChatbotArena Elo 接近（2025-11-10 评测时点）；独立长上下文评测中 AA-LCR 在 reasoning mode 下高出 4 分、Fiction.liveBench 多指标胜出。前者是内部对照，后者是第三方佐证，组合起来基本闭合了「稀疏化无损」的主张，但幅度有限的正向差也提示这确实是 parity 而非 upgrade。

### 4.2 主成绩全景（Table 2，p13，V3.2-Thinking）

- **知识/科学**：MMLU-Pro 85.0、GPQA-Diamond 82.4、HLE 25.1（官方模板下 23.9）；
- **数学**：AIME2025 93.1、HMMT-Feb 92.5、HMMT-Nov 90.2、IMO-AB 78.3；
- **代码**：LiveCodeBench 83.3、Codeforces 2386 rating；
- **Agentic Code**：Terminal-Bench 2.0 46.4（ClaudeCode 框架）、SWE-Verified 73.1（跨框架鲁棒区间 72–74）、SWE-Multilingual 70.2；
- **Search**：BrowseComp 51.4、加 context management 后 67.6*、BrowseCompZh 65.0；
- **Tool Use**：τ-bench 80.3（Airline 63.8 / Retail 81.1 / Telecom 96.2）、MCP-Universe 45.9、MCP-Mark 38.0、Tool-Decathlon 35.2。

横向定位：推理能力与 GPT-5-High 相当、略逊 Gemini-3.0-Pro；对比 Kimi-K2-Thinking 以**显著更少输出 token** 取得相当分数；SWE 与 Terminal-Bench 显著超越开源对手（§4.1，p13–14）。

### 4.3 Token 效率证据（Table 3，p15）

V3.2-Thinking 的平均输出 token 显著低于 K2-Thinking：AIME25 上 16k vs 24k，IMO-AB 上 27k vs 37k，精度相当。这说明「更省的思考」本身就是可量化的竞争力。反方向的证据来自 Speciale：77k token @ Codeforces 换更高峰值精度——同一基座上效率点与精度点的显式权衡。

### 4.4 Speciale 峰值证据（Table 3/4，p15）

AIME25 96.0（23k token）、HMMT-Feb 99.2（27k）、IMO-AB 84.5（45k），多项超过 Gemini-3.0-Pro；但 token 效率仍显著劣于对方。无针对性训练的奥赛成绩：IMO2025 35/42 金牌、CMO2025 102/126 金牌、IOI2025 492/600 金牌（第 10 名）、ICPC-WF2025 10/12 金牌（第 2 名），全部金牌档位。

### 4.5 合成任务双消融（§4.3，Table 5 / Figure 5，p15）

**难度有效性**：50 个 general 合成任务抽样上，V3.2-Exp 仅 12% 准确率、前沿闭源模型最高 62%——合成集对所有前沿模型都足够难，排除了「任务太水导致虚高」的质疑。**泛化有效性**：在 SFT checkpoint 上仅用合成 agentic 数据做 non-thinking RL，即可观察到对下游真实环境的显著迁移提升，且评测所用的环境与工具集均未在 RL 中出现——这是 out-of-domain 泛化的直接证据。

### 4.6 成本证据（Figure 3，p6）

H800 集群实测（$2/GPU·小时定价口径）：prefill 与 decode 的每 token 成本随序列位置的增长显著低于 V3.1-Terminus，decode 在 128K 位置约为 $0.1 vs $0.4 每百万 token 的量级差。这是 DSA 经济价值最直观的兑现形式。

### 4.7 证据强度分级

（推断）按可信度分层：Table 2/Table 3/Table 4 为一手自报实测（有跨框架复核与第三方榜单交叉）；AA-LCR/Fiction.liveBench 为独立评测佐证（中等强度）；成本曲线依赖自报集群与电价假设（方向可信、绝对值需自行折算）；「合成任务泛化到真实世界」的结论目前只有 out-of-domain 基准证据，尚缺真实用户流量回归（源数据 §6.6 亦承认此点）。

## 五、批判性分析

**（1）Parity 的隐藏成本由长尾用户承担。** 约 **20%+ 的 BrowseComp 测试样例超出 128K 上下文**（p14 §4.1），需 context management 补救才有 67.6*，裸分 51.4。换言之，「无损」是在 128K 窗口内成立的长程承诺，窗口之外的用户必须自建补救层。对以长文档为核心负载的场景，这是一笔被基准分数遮蔽的真实成本。

**（2）冗余自我验证行为未被根治。** 模型频繁生成过长的验证轨迹，在 MCP-Mark 的 GitHub/Playwright 类任务上常撑爆 128K 限窗直接拖累得分（作者列为 future work）。这与 Speciale「靠堆 token 冲精度」的成功互为镜像：同一个「多想」倾向，在受限窗口里是负债，在开放预算里是资产。行为层面的预算控制仍是未解问题。

**（3）Token 效率与闭源旗舰存在代差。** Speciale 精度虽超 Gemini-3.0-Pro，但 token 效率「仍显著劣于」（p15）。考虑到推理服务的边际成本主要由输出 token 决定，这一劣势会在商业化定价上被放大；论文亦承认 token 效率是未来关键方向。

**（4）框架兼容性是隐性生态税。** Thinking 模式的 context management 与 Terminus 框架不兼容——Terminal-Bench 2.0 的 46.4 必须换 ClaudeCode 框架取得，Terminus 下 non-thinking 仅 39.3；RooCode 类框架同样无法受益。46.4 与 39.3 之间近 7 分的差距，本质上是「协议红利」而非「模型红利」，它要求下游用户理解并适配特定的消息构造方式，抬高了集成门槛。

**（5）DSA 是止损不是增益。** 架构改动的全部绩效主张建立在「不变得更差」之上；AA-LCR +4 属外部佐证且幅度有限。对多数短上下文应用而言，DSA 带来的收益接近于零（短序列甚至要走 MHA 模拟路径），其价值高度集中于 32K–128K 的长上下文区间（推断：收益区间的具体边界论文未给出，此处依成本曲线形状推断）。

**（6）Indexer 的单点依赖。** （推断）Top-k 选择的质量完全系于 lightning indexer 的打分精度，而 KL 对齐只能保证「分布意义上接近 dense 归一化注意力」，不能保证逐样本最优。错误排除强相关 token 的风险由主模型的 LM loss 隐式吸收，论文未提供「选择命中率」或「关键 token 召回率」的直接度量，稀疏化损失的微观归因是黑箱。

**（7）k=2048 的普适性未经检验。** 论文实验固定 k=2048，未见对 k 的系统消融。检索型任务（少量 needle）与聚合型任务（全篇摘要式推理）的最优 k 理应不同（推断）；固定 k 的「一刀切」可能在两类任务间留下效率或质量的余量未榨取。

**（8）评测敏感性的信号。** HLE 在官方模板下 23.9、自报模板 25.1，2.1 分的模板差提示：在旗舰级分数带上，评测协议的选择已足以改变相对排名的叙事，跨模型对比需谨慎对待模板差异。

**（9）合成环境的模拟鸿沟。** General Agent 环境全部合成（沙盒数据库 + 自造工具），「难解易验」保证了任务难度与可判定性，但对真实世界工具分布的覆盖依赖 out-of-domain 泛化检验；search/code 的 prompt 也非来自真实用户交互（p10 §3.2.3 自述）。实验室泛化与野外泛化之间的距离，需要真实流量回归来测量——目前缺席。

## 六、启示与影响

**（1）「唯一架构改动」的渐进演进范式。** 相对 V3.1-Terminus 只动注意力一处、其余全盘继承，通过 943.7B tokens 续训完成切换——这为大模型时代的架构升级提供了模板：把激进改动封装在可续训、可验证 parity 的最小增量里，让生态（权重、推理栈、微调脚本）以最低成本跟进。

**（2）Detach 式模块解耦是稀疏化训练的通用钥匙。** 「辅助模块只吃蒸馏/KL 监督、主干只吃任务损失」的训练隔离思路，可推广到一切「预测器 + 消费者」结构的系统（推测器、路由器、检索器）（推断）。它以牺牲端到端联合优化为代价，换来训练稳定性与故障可归因性，在超大尺度上这笔交换大概率是划算的。

**（3）RL 稳定技术四件套进入公共领域。** 无偏 KL、负样本 off-policy 掩码、KeepRouting、KeepSamplingMask 都是「一行描述就能懂」的工程修补，却各自封堵一类真实的崩塌模式。对任何试图把 GRPO 推到千卡规模的团队，这四项应视作 checklist 级别的默认配置。

**（4）「难解易验」是合成环境的四字心法。** solution function 锁死工具接口、verification function 保证可判定、逐步加难度、pass@100>0 过滤——这套组合拳把「环境生成」从玄学变成工艺，可直接移植到任何可验证领域（数学、代码、游戏规则类任务）（推断：对主观评价类任务适用性有限，因 verifier 难以形式化）。

**（5）思考链管理将成为框架层的标准议题。** 「新 user 消息才丢推理、tool 追加则保留」的规则，实质是把 KV 显存变成了可编程资源。谁控制消息流协议，谁就控制 thinking 模型的实际能力发挥——Terminus 与 ClaudeCode 近 7 分的 Terminal-Bench 差距就是明证。推理框架的消息协议标准化将被加速提上日程（推断）。

**（6）效率-精度双产品线是旗舰模型的新形态。** 正式版压 token、Speciale 放开 token 冲峰值的二元布局，暗示未来的旗舰发布可能标配「经济档 + 峰值档」双变体，让同一基座覆盖从日常对话到奥赛冲刺的全谱系需求。

**（7）开源竞争的主战场迁移。** 当开源模型在 SWE-Verified（73.1）等硬基准上显著超越开源对手、逼近闭源第一梯队时，竞争焦点将从「能力有无」转向「每 token 能力的单价」——DSA 给出的 O(L²)→O(Lk) 曲线与 H800 实测账单，正是这场成本战争的第一次公开报价。
